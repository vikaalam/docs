> **The reflex layer.** Two ingress doors, one matcher, and an ordered list of independent actions.
> Stateless per event: nothing is ever "in progress" here.

| | |
| --- | --- |
| Schema | `automation` |
| Layer | Reflex |
| Depends on | `process`, `task`, `notification`, `integration`, `directory`, `reporting` — all via `client/` |
| Depended on by | *nothing — it is the top of the call graph and the **only stream reader*** |
| Slice | **1 — Reflex** |
| Extraction trigger | Ingest volume needs a scaling profile the rest of the platform does not |

## Why it is its own module

`automation` is the platform's front door. Everything that happens anywhere — an external system's
fact, a task reaching a terminal state, a provider callback completing — arrives here as an event and
leaves as an ordered list of actions.

<Note>
  **It is separate from `process` for one reason: it holds no state between events.** An event is
  matched, intent is written, and the event is done.

  If it had to remember that step 2 of a case finished while step 3 waits for a person, it would be a
  state machine living inside a stream consumer — the exact failure this architecture is built to
  avoid.
</Note>

It is **not** split into `automation` + `workflow`. A workflow *is* automation's core concept: the
ordered action list bound to a matched event type. Separating the trigger from what it triggers pays
the full price of a module boundary for nothing.

## Internal structure

```
automation/internal/
├── ingest/      both doors, the guards, the ingest row
├── matcher/     condition evaluation, priority ordering, exclusive short-circuit
├── actions/     the eight action types, each dispatched through a client/
└── dispatch/    the outbox pump for events this module publishes
```

<Note>
  **These tables are partitioned:** `action_executions` · `ingested_events`.

  A partitioned table **cannot carry a global unique constraint**, which is why `action_execution_keys` and `event_keys` exists beside it, unpartitioned. An ER diagram cannot express that, so it is stated here.
</Note>

<Warning>
  **No relationship line leaves this schema, and that is the boundary rule rather than an omission.** The 2 lines above are real foreign keys inside `automation`.

  Bare cross-schema references — drawn nowhere, because the database does not enforce them: **Zero** — `automation` names subjects, never other modules' rows. Its cross-module reach is the eight action types, not a column.
</Warning>

Three of those exist **because a partitioned table cannot carry the unique constraint its module
depends on** — see [idempotency](/engineering/events/idempotency).

## The rules this module implements

| Rule | Where it is specified |
| --- | --- |
| Two doors, one identical matcher | [Ingress](/engineering/events/ingress) |
| The envelope, and the seven forbidden fields | [Envelope](/engineering/events/envelope) |
| Four guards — duplicate, depth, cycle, action re-execution | [Idempotency](/engineering/events/idempotency) |
| All matching workflows run; priority orders; exclusive overrides | [Matching](/engineering/events/matching-and-actions) |
| Eleven ingest statuses and their precedence | [Lifecycle](/engineering/events/lifecycle) |
| The continuous retention invariant | [Lifecycle](/engineering/events/lifecycle) |

## Being the only stream reader

<Note>
  Internal modules are publishers **exactly like external systems**. That is what makes "two doors,
  one pipeline" true for internal traffic as well.

  It also puts ordering, idempotency, and **both loop guards** in one place instead of four — which is
  the entire argument against per-module stream consumers.
</Note>
