## The stack

**NestJS 11 · PostgreSQL 17 · Redis 7 (Streams) · Vue 3 + Vite SPA.** One deployable process, one
database instance, **one schema per module**.

<Warning>
  **There is no product code yet.** This is a design spike. The planned source layout is specified,
  not runnable.

  What *does* exist is listed at the bottom of this page, and it is more than documents.
</Warning>

  **`audit` appears in neither column, and that is the point.** Nothing calls it, and it publishes
  nothing — which is why it owns no outbox, and why it is the one module that can never be extracted.
</Note>

## The one rule that keeps the graph acyclic

<Note>
  **Calls downward are synchronous, through `client/`. Returns upward are asynchronous, through
  events.**
</Note>

This is not a stylistic preference. It is the only thing preventing the two cycles this design would
otherwise have:

- **`task` must never know `process` exists.** When a task reaches a terminal state it publishes
  `task.item.state_changed` to its outbox. That event goes to the stream, re-enters through ingest
  like any external event, and matches a workflow whose action is `signal_process`. A direct call
  would make `process → task → process` a cycle — and, worse, would stop `task` being usable for
  ad-hoc work that belongs to no process.
- **`integration` must never know `process` exists.** An asynchronous provider result returns the
  same way.

The cost is one Redis round trip per resumption. Two things are bought: the resumption is **durable**
(it survives a restart on either side) and **visible** (internal transitions appear in the same
ingest history as external events, so the entire operational timeline is one queryable list).

## What has actually been produced

Beyond the specification itself, five generated artefacts exist — **all of them output of the
documents rather than sources.**

| Artefact | What it is | Generated from |
| --- | --- | --- |
| Per-schema migrations | **65 base tables plus 6 partition children — 71 physical tables across 9 schemas.** Verified by applying all nine together to PostgreSQL and checking the conventions against the system catalogue — not against the SQL text | Each module's data model, plus the cross-schema section |
| [Event envelope JSON Schema](/api/event-envelope) | The envelope, machine-readable. The seven forbidden fields are **declared**, so a validator names the offender rather than shrugging | The event contract |
| [OpenAPI specification](/api) | The HTTP surface — 84 paths, 92 operations. **Harvested, not designed:** only two paths are named above the design layer | The endpoints the module and screen documents already name |
| Seeded event types | **139 registered event types.** Domain vocabulary is permitted here and nowhere else in the core | The event catalogue |
| Boundary and vocabulary gates | Dependency rules, lint rules, the domain-term list, and the check script | The boundary rules and the company-agnostic rule |

<Warning>
  **The generated artefacts are output and must never be edited to resolve a disagreement.** If a
  migration and a module data model differ, the migration is wrong. Regenerate; do not patch.
</Warning>

<Note>
  **The table count was re-measured on 2026-07-28 and had drifted.** An earlier figure of *58 table
  names, 64 physical tables* is superseded: counting `CREATE TABLE` statements across the nine
  migration files gives **65 base tables and 6 partition children**.

  Per schema: `automation` 13 · `directory` 9 · `integration` 9 · `process` 7 · `reporting` 6 ·
  `task` 6 · `audit` 5 · `notification` 5 · `platform` 5.

  The correction is recorded rather than substituted silently, for the same reason the send-site
  counts carry theirs: **a checkable number that is wrong costs more than one never claimed.**
</Note>

## Two things that run today

```bash
python3 tools/design-sync.py   # twelve checks: does design/ still describe the architecture,
                               # and does the architecture still agree with the modules?
./tools/arch-check.sh          # the company-agnostic gate
```

<Note>
  The twelve design-sync checks have **each been proven to fail against an injected defect**, so a
  clean run means something. A gate that has never rejected anything is not a gate; it is a config
  file.
</Note>
